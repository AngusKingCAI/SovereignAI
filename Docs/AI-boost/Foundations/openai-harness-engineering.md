# Harness Engineering: Leveraging Codex in an Agent-First World

**Source:** https://openai.com/index/harness-engineering/
**Author:** Ryan Lopopolo, Member of the Technical Staff
**Date:** February 11, 2026

---

## Overview

Over the past five months, our team has been running an experiment: building and shipping an internal beta of a software product with **0 lines of manually-written code**.

The product has internal daily users and external alpha testers. It ships, deploys, breaks, and gets fixed. What's different is that every line of code—application logic, tests, CI configuration, documentation, observability, and internal tooling—has been written by Codex. We estimate that we built this in about 1/10th the time it would have taken to write the code by hand.

**Humans steer. Agents execute.**

We intentionally chose this constraint so we would build what was necessary to increase engineering velocity by orders of magnitude. We had weeks to ship what ended up being a million lines of code. To do that, we needed to understand what changes when a software engineering team's primary job is no longer to write code, but to design environments, specify intent, and build feedback loops that allow Codex agents to do reliable work.

This post is about what we learned by building a brand new product with a team of agents—what broke, what compounded, and how to maximize our one truly scarce resource: human time and attention.

## We Started with an Empty Git Repository

The first commit to an empty repository landed in late August 2025.

The initial scaffold—repository structure, CI configuration, formatting rules, package manager setup, and application framework—was generated by Codex CLI using GPT‑5, guided by a small set of existing templates. Even the initial AGENTS.md file that directs agents how to work in the repository was itself written by Codex.

There was no pre-existing human-written code to anchor the system. From the beginning, the repository was shaped by the agent.

Five months later, the repository contains on the order of a million lines of code across application logic, infrastructure, tooling, documentation, and internal developer utilities. Over that period, roughly 1,500 pull requests have been opened and merged with a small team of just three engineers driving Codex. This translates to an average throughput of 3.5 PRs per engineer per day, and surprisingly the throughput has increased as the team has grown to now seven engineers. Importantly, this wasn't output for output's sake: the product has been used by hundreds of users internally, including daily internal power users.

Throughout the development process, humans never directly contributed any code. This became a core philosophy for the team: **no manually-written code**.

## Redefining the Role of the Engineer

The lack of hands-on human coding **introduced a different kind of engineering work, focused on systems, scaffolding, and leverage**.

Early progress was slower than we expected, not because Codex was incapable, but because the environment was underspecified. The agent lacked the tools, abstractions, and internal structure required to make progress toward high-level goals. The primary job of our engineering team became enabling the agents to do useful work.

In practice, this meant working depth-first: breaking down larger goals into smaller building blocks (design, code, review, test, etc), prompting the agent to construct those blocks, and using them to unlock more complex tasks. When something failed, the fix was almost never "try harder." Because the only way to make progress was to get Codex to do the work, human engineers always stepped into the task and asked: "what capability is missing, and how do we make it both legible and enforceable for the agent?"

Humans interact with the system almost entirely through prompts: an engineer describes a task, runs the agent, and allows it to open a pull request. To drive a PR to completion, we instruct Codex to review its own changes locally, request additional specific agent reviews both locally and in the cloud, respond to any human or agent given feedback, and iterate in a loop until all agent reviewers are satisfied (effectively this is a Ralph Wiggum Loop). Codex uses our standard development tools directly (gh, local scripts, and repository-embedded skills) to gather context without humans copying and pasting into the CLI.

Humans may review pull requests, but aren't required to. Over time, we've pushed almost all review effort towards being handled agent-to-agent.

## Increasing Application Legibility

As code throughput increased, our bottleneck became human QA capacity. Because the fixed constraint has been human time and attention, we've worked to add more capabilities to the agent by making things like the application UI, logs, and app metrics themselves directly legible to Codex.

For example, we made the app bootable per git worktree, so Codex could launch and drive one instance per change. We also wired the Chrome DevTools Protocol into the agent runtime and created skills for working with DOM snapshots, screenshots, and navigation. This enabled Codex to reproduce bugs, validate fixes, and reason about UI behavior directly.

We did the same for observability tooling. Logs, metrics, and traces are exposed to Codex via a local observability stack that's ephemeral for any given worktree. Codex works on a fully isolated version of that app—including its logs and metrics, which get torn down once that task is complete. Agents can query logs with LogQL and metrics with PromQL. With this context available, prompts like "ensure service startup completes in under 800ms" or "no span in these four critical user journeys exceeds two seconds" become tractable.

We regularly see single Codex runs work on a single task for upwards of six hours (often while the humans are sleeping).

## We Made Repository Knowledge the System of Record

Context management is one of the biggest challenges in making agents effective at large and complex tasks. One of the earliest lessons we learned was simple: **give Codex a map, not a 1,000-page instruction manual.**

We tried the "one big AGENTS.md" approach. It failed in predictable ways:
- **Context is a scarce resource.** A giant instruction file crowds out the task, the code, and the relevant docs—so the agent either misses key constraints or starts optimizing for the wrong ones.
- **Too much guidance becomes non-guidance.** When everything is "important," nothing is. Agents end up pattern-matching locally instead of navigating intentionally.
- **It rots instantly.** A monolithic manual turns into a graveyard of stale rules. Agents can't tell what's still true, humans stop maintaining it, and the file quietly becomes an attractive nuisance.
- **It's hard to verify.** A single blob doesn't lend itself to mechanical checks (coverage, freshness, ownership, cross-links), so drift is inevitable.

So instead of treating `AGENTS.md` as the encyclopedia, we treat it as **the table of contents**.

The repository's knowledge base lives in a structured `docs/` directory treated as the system of record. A short `AGENTS.md` (roughly 100 lines) is injected into context and serves primarily as a map, with pointers to deeper sources of truth elsewhere.

### Plain Text

```
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/
│   ├── index.md
│   ├── core-beliefs.md
│   └── ...
├── exec-plans/
│   ├── active/
│   ├── completed/
│   └── tech-debt-tracker.md
├── generated/
│   └── db-schema.md
├── product-specs/
│   ├── index.md
│   └── ...
├── technical-standards/
│   ├── index.md
│   └── ...
└── workflows/
    ├── index.md
    └── ...
```

### Key Design Principles

1. **Plain text everywhere** - AGENTS.md, ARCHITECTURE.md, and all docs are plain text. This makes them directly legible to Codex without any special tooling.
2. **Mechanical verification** - We run automated checks to ensure docs stay in sync with reality. Cross-links are validated, ownership is tracked, and coverage is measured.
3. **Incremental relevance** - Instead of dumping everything into context, we let Codex discover what it needs through a combination of index files and targeted queries.
4. **Self-healing** - We have agents that periodically review docs for freshness and flag or update stale content.

## Agent Legibility is the Goal

The core insight is that **agent legibility is the primary design constraint**. If you want agents to work effectively in your codebase, you need to design for their understanding—not just human understanding.

This has implications across the board:
- **Architecture** should be explicit and well-documented, not implicit and inferred
- **Code structure** should follow predictable patterns that agents can learn
- **Tests** should be comprehensive and serve as executable documentation
- **Error messages** should be actionable and guide agents toward fixes
- **APIs** should be designed with clear contracts that agents can reason about

When we design for agent legibility, we often end up designing for human legibility too—but the priority is inverted. We optimize for the agent first, knowing that humans can handle a bit more complexity than agents can.

## Enforcing Architecture and Taste

One of the biggest fears with agent-generated code is that it will become a tangled mess of inconsistent patterns and architectural violations. To prevent this, we built deterministic enforcement systems into the harness.

### Linters and Structural Tests

We have a comprehensive set of linters and structural tests that run on every PR. These are not style guides—they're architectural constraints expressed as code:
- Directory structure violations (files in wrong locations)
- Import cycle detection
- API contract validation
- Data flow integrity checks
- Performance regression guards

If a PR fails any of these checks, it cannot merge. Codex learns this constraint the same way human engineers do: by running the checks, seeing failures, and fixing them.

### Architectural Reviewers

We also have agent reviewers that specialize in architectural compliance. These reviewers:
- Check that changes align with documented architecture
- Verify that patterns are used consistently
- Flag violations of core design principles
- Suggest refactors when appropriate

These reviewers run automatically on every PR and can block merges if they find architectural violations.

## Throughput Changes the Merge Philosophy

When you're shipping 3.5 PRs per engineer per day, traditional code review becomes a bottleneck. We've had to adapt our merge philosophy to match this throughput.

### Agent-to-Agent Review

The default is agent-to-agent review. Human review is reserved for:
- Security-sensitive changes
- Major architectural decisions
- Changes that affect user-facing behavior
- PRs that fail automated checks

This doesn't mean humans are disengaged—it means humans are engaged at a higher level of abstraction. Instead of reviewing every line of code, humans review:
- System architecture and design
- Agent behavior and effectiveness
- Overall system health and direction
- Strategic decisions about the product

### Faster Failures

With high throughput, we've embraced faster failures. If a PR introduces a bug, we'd rather discover it quickly through automated testing and fix it in the next PR than spend hours trying to prevent every possible failure up front.

This is enabled by:
- Comprehensive test coverage
- Fast test execution
- Automated rollback capabilities
- Feature flags for safe rollouts

## What "Agent-Generated" Actually Means

We use the term "agent-generated" deliberately. It doesn't mean "agent-authored" in the sense that the agent is the sole creative force. It means:

1. **Agents write the code** - Every line of code is written by Codex, not by humans
2. **Humans design the harness** - Humans design the environment, tools, and constraints that shape agent behavior
3. **Agents drive the process** - Agents handle the day-to-day work of implementation, testing, and iteration
4. **Humans provide high-level direction** - Humans set goals, review outcomes, and adjust the harness as needed

The distinction matters because it clarifies what humans are responsible for. Humans are not code reviewers in the traditional sense—they're harness engineers who design systems that enable agents to do reliable work.

## Increasing Levels of Autonomy

Over the five months, we've gradually increased the level of autonomy we give Codex. This wasn't a binary switch from "no autonomy" to "full autonomy"—it was a progression through multiple levels:

### Level 1: Task Execution
Codex executes specific tasks that humans describe in detail. The human provides the what, why, and how.

### Level 2: Task Decomposition
Codex breaks down high-level goals into smaller tasks and executes them. The human provides the what and why; Codex figures out the how.

### Level 3: System Design
Codex designs and implements entire features or subsystems. The human provides the what; Codex figures out the why and how.

### Level 4: Strategic Decision Making
Codex makes strategic decisions about system architecture, trade-offs, and direction. The human provides high-level constraints and goals; Codex fills in the details.

We're currently operating at Level 3 for most work, with some Level 4 tasks for well-scoped areas. The progression has been deliberate: we only increase autonomy when we've built sufficient guardrails and verification systems.

## Entropy and Garbage Collection

Even with well-designed harnesses, entropy is inevitable. Over time, documentation drifts, code accumulates technical debt, and the system becomes harder to understand and modify.

To combat this, we've built garbage collection agents that periodically:
- Review documentation for freshness and accuracy
- Identify and flag dead code
- Suggest refactors for complex or inconsistent areas
- Update architectural documentation to reflect reality
- Clean up unused dependencies and configurations

These agents run on a schedule (daily for some checks, weekly for others) and can make non-breaking changes automatically. Breaking changes require human review.

The key insight is that **maintenance is also agent work**. We don't rely on humans to stay on top of entropy—we give agents the tools and authority to handle it themselves.

## What We're Still Learning

This is still an experiment, and we're learning constantly. Some areas where we're still figuring things out:

### Debugging Complex Failures
When something goes wrong in a complex interaction between multiple agents and systems, debugging can be challenging. We're investing in better observability and debugging tools specifically for agent systems.

### Managing Agent Identity
As we use Codex for more tasks, we need better ways to manage different "personalities" or configurations of Codex for different types of work. We're exploring agent profiles and context-switching mechanisms.

### Balancing Speed and Quality
High throughput is great, but not at the expense of quality. We're still tuning the balance between speed of delivery and robustness of the system.

### Knowledge Transfer
How do we transfer what we've learned to other teams? We're documenting our harness design patterns and creating reusable templates that other teams can adopt.

### Long-Term Sustainability
Can this scale? Can we maintain this level of productivity over years rather than months? We don't know yet, but we're optimistic that well-designed harnesses can sustain high productivity over the long term.

## Key Takeaways

1. **Harness engineering is a discipline** - Designing environments for agents is a distinct skill that needs to be learned and practiced
2. **Agent legibility is the primary constraint** - Design for agent understanding first, human understanding second
3. **Repository knowledge is the system of record** - Treat docs as the source of truth, not as supplementary material
4. **Enforcement is critical** - Build deterministic systems that prevent architectural violations
5. **Autonomy is a spectrum** - Increase autonomy gradually as you build guardrails
6. **Entropy is inevitable** - Build garbage collection agents to maintain system health
7. **Humans are harness engineers** - The human role shifts from writing code to designing systems
