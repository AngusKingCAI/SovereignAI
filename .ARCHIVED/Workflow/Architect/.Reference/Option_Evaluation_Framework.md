# Architect Option Criteria

**Purpose**: Architect-specific criteria for generating and evaluating implementation options.

## Architect Option Criteria Specifications

### Viable Option Criteria

**Different Mechanism of Action**
- Options must represent distinct approaches, not cosmetic variations
- Each option should use a fundamentally different method or technique
- Avoid options that are essentially the same approach with minor differences
- Ensure meaningful differentiation between options

**Feasible Execution**
- Options must be aligned with available time, budget, and capabilities
- Consider resource constraints and limitations
- Ensure options are realistically implementable
- Account for technical and operational feasibility

**Evaluability**
- Options must be assessable against defined criteria
- Enable clear comparison and evaluation
- Provide measurable outcomes and success criteria
- Allow for objective assessment and selection

## Option Requirements

### Each Option Must Include

**Summary**
- Clear description of what the option does
- Explanation of the approach and methodology
- Overview of expected outcomes
- Key characteristics and features

**Impact Score (out of 10)**
- Assessment of the option's impact on the system
- Reasoning for the impact score
- Consideration of both positive and negative impacts
- Alignment with architectural goals

**Effort Score (out of 10)**
- Assessment of implementation effort required
- Reasoning for the effort score
- Consideration of time, resources, and complexity
- Feasibility within project constraints

**Risk Score (out of 10)**
- Assessment of potential risks and uncertainties
- Reasoning for the risk score
- Consideration of technical, operational, and business risks
- Mitigation strategies for identified risks

## Option Generation Process

### Research-Based Generation
- Base options on research findings and best practices
- Consider industry standards and established patterns
- Incorporate lessons learned from similar implementations
- Ensure options are grounded in current best practices

### Architect Opinion Framework
- Provide analysis and recommendation BEFORE user selection
- Explain reasoning behind recommendations
- Consider trade-offs between options
- Align with architectural principles and constraints

### Presentation Pattern
- Present options with clear metrics and scores
- Provide architect opinion alongside objective criteria
- Use popup menu for user selection
- Ensure transparency in evaluation process

### Rule Enforcement
- Ensure options comply with .devin/rules/architect.md
- Validate options against governance constraints
- Consider security and compliance requirements
- Ensure options align with architectural boundaries

## Usage Guidelines

### When Generating Options
1. **Research First**: Conduct thorough research before generating options
2. **Apply Criteria**: Use viable option criteria to filter and refine options
3. **Score Objectively**: Score options objectively using defined metrics
4. **Provide Context**: Include reasoning and context for each score
5. **Recommend Wisely**: Provide architect opinion based on analysis

### When Evaluating Options
1. **Review Criteria**: Review option criteria for compliance
2. **Assess Scores**: Evaluate impact, effort, and risk scores
3. **Consider Trade-offs**: Weigh pros and cons of each option
4. **Validate Compliance**: Ensure options comply with architectural rules
5. **Select Appropriately**: Select option that best meets requirements
